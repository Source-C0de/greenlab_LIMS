# Open Questions / Gaps

> These are decisions the backend team should **resolve before
> implementation starts** (or at least before each respective phase).
> Each gap has a recommended default in **bold** so you can accept it
> and move on if no product input is needed.

## G1 — ZATCA integration vendor

**The spec assumes server-side ZATCA FATOORA compliance** — `uuid`,
`hash`, `qrCode` (TLV-encoded base64), `irn` are all generated by the
backend when an invoice is reported. The SPA's current
`src/lib/accounting-utils.ts` `ZatcaService` is **mock-only** math
that must be replaced wholesale.

**Recommended default:** integrate with one of:
- ZATCA's official SDK + a managed e-invoicing provider (e.g.
  [Sila](https://silamoney.com), [Foodics](https://foodics.com),
  [Lean](https://www.leantech.me), or local Saudi providers like
  [Tharwah](https://tharwah.net) or [Sahab Plus](https://sahabplus.sa)).
- A direct ZATCA sandbox integration (free; harder; not for production).

**Decision needed:** which vendor, which sandbox creds.

## G2 — Sample ID generation authority

The SPA today generates sample IDs client-side
(`src/lib/sample-id.ts:18-43`, used at
`src/pages/samples/receiving.tsx:88-100`). For a multi-user backend,
this is unsafe — two concurrent receptions would mint colliding IDs.

**Recommended default:** server-mints the ID inside the same
transaction that creates the sample row, using a Postgres sequence
per `(prefix, year)` pair:

```sql
CREATE SEQUENCE sample_serial_fd_2026 START 1;
CREATE SEQUENCE sample_serial_wt_2026 START 1;
-- ...
```

Format stays `<PREFIX>/<YYYY>/<NNNN>` so the SPA's wouter splat route
keeps working unchanged.

**Decision needed:** confirm the format stays 4-digit serial (today) vs.
expand to 6-digit (for high-throughput labs). Default: **4-digit**.

## G3 — File storage for signatures & attachments

The SPA references static `dist/signatures/*.png` files via string
URLs (`src/mock-data/analysts.ts`, `src/mock-data/reports.ts`). Real
employee signatures need to be uploaded and stored somewhere.

**Recommended default (v1):** local disk under `/var/greenlims/uploads/`,
served via Nginx at `/uploads/<uuid>.png`. Migrate to S3-compatible
(DigitalOcean Spaces, MinIO) in v2.

**Decision needed:** v1 disk vs. v2 Spaces — default: **disk**.

## G4 — Idempotency for invoice reporting

`POST /api/v1/invoices/:id/report-zatca` is a state-changing external
call to ZATCA. If the request times out and the frontend retries, we
risk double-reporting (and double-IRN).

**Recommended default:** require `Idempotency-Key` header on this
endpoint (Stripe-style). Server stores `(invoiceId, idempotencyKey) →
response` for 24h and replays the cached response on duplicate keys.

**Decision needed:** accept the default. (`backend.md` doesn't mention
this; it's an addition.)

## G5 — Timezone policy

The SPA displays dates in browser-local time
(`Intl.DateTimeFormat()` with no explicit timezone). All sample
creation times, invoice issue dates, journal dates are stored as
`YYYY-MM-DD` (date-only) or ISO-8601 UTC (timestamps).

**Recommended default:**
- Date-only fields (`receivedDate`, `issueDate`, `dueDate`,
  `expiryDate`, `issuanceDate`) — store as `DATE` in Postgres, format
  as `YYYY-MM-DD` over the wire. The frontend formats for display.
- Datetime fields (`createdAt`, `submittedAt`, `lastLoginAt`) — store
  as `timestamptz` in Postgres (UTC), format as ISO-8601 with `Z`
  suffix. The frontend formats with `Intl.DateTimeFormat("en-SA")` or
  `"ar-SA"`.
- Server clock in `Asia/Riyadh` (UTC+3, no DST).

**Decision needed:** confirm. Default: **UTC storage + Asia/Riyadh
display**.

## G6 — CSRF strategy on cookies

The auth model is httpOnly cookie. State-changing requests are
vulnerable to CSRF. The OpenAPI spec marks these with `x-csrf: true`
and lists two acceptable strategies in [`README.md`](./README.md#csrf).

**Recommended default:** **double-submit cookie**.
- Login sets `glims_session` (HttpOnly) **and** `glims_csrf` (readable
  by JS).
- The frontend reads `glims_csrf` once on app mount and echoes it in
  `X-CSRF-Token` on every POST/PUT/PATCH/DELETE.
- Server middleware rejects requests missing or mismatching the header
  (except `Origin` allowlisted routes like the login itself).

**Decision needed:** confirm double-submit. Alternative: **same-site
strict + origin check** is slightly less code but breaks if the SPA
ever needs to be embedded in another origin.

## G7 — Multi-tenant deprecation path

The decision is **single-tenant in v1**, but `tenants.ts` exists as
mock data and `admin.tsx` renders a Tenants tab. If the SaaS-onboarding
story returns later, the simplest migration is:

1. Add a `tenantId` column to every domain table (nullable).
2. Set `default` row id as the only seed.
3. Add a `tenantId` claim to the JWT.
4. Add row-level filters in every query.

**Recommended default:** design every schema now to **include a
nullable `tenant_id`** column, even if always set to `default`. Cheap
insurance.

**Decision needed:** include `tenant_id` column from day 1 (default
**yes**).

## G8 — Approval state machine: who can approve at which stage

The SPA's 3-stage approval (`lab_supervisor → tech_manager → qa`) is
hardcoded in `samples.ts:139-147` (`currentStage()`). In a multi-role
lab, the per-stage role might be configurable.

**Recommended default (v1):** hardcode the three stages server-side,
but record `approverRole` on each `StageApproval` so the UI can show
"approved by <Name> as <Role>". Make stage-to-role configurable in v2.

**Decision needed:** confirm. Default: **hardcoded stages, configurable
roles per tenant in v2**.

## G9 — Bulk operations and pagination caps

The spec uses `?pageSize=` (max 200). Bulk endpoints like
`POST /api/v1/tests/bulk-approve` accept a `testIds: string[]` body.

**Recommended default:** cap `testIds.length` at 100 per request;
larger batches must chunk client-side.

**Decision needed:** confirm. Default: **100**.

## G10 — Idempotency for `POST /samples` and other creates

Sample creation has a unique constraint problem: if the analyst
double-clicks "Receive", two samples get created. The form needs a
client-generated `requestId` echoed in an `Idempotency-Key` header.

**Recommended default:** same as G4 — require `Idempotency-Key` on
all `POST` endpoints that create top-level resources (`/samples`,
`/clients`, `/invoices`, `/journals`, `/specifications`,
`/reagents`). Server caches `(userId, key) → response` for 24h.

**Decision needed:** accept the default.

## G11 — Audit log

`backend.md` §10 defers audit logging. The superadmin legacy spec
already has one (`docs/SUPERADMIN_API.md` §E). For a single-tenant
LIMS handling ISO-17025-accredited labs, an audit trail of every
state transition is a hard requirement in production.

**Recommended default (v1):** minimal audit log on writes only.
Table `audit_log` with `(id, actorId, action, targetType, targetId,
metadata, createdAt)`. Mirror every write in `services/audit.py`.

**Decision needed:** accept v1 = audit-only, defer UI. Default: **yes**.

## G12 — Notification delivery

The SPA's `NotificationContext` reads from `mockNotifications` (in-app
only). For real-time push, the backend would need SSE or WebSockets.

**Recommended default (v1):** in-app only — `GET /notifications`
polled on mount and every 60s. WebSocket/SSE in v2.

**Decision needed:** confirm. Default: **polling**.

## G13 — Search

The SPA's `DataTable` does client-side substring search. For real
backends this becomes a server concern. The spec uses `?q=` for free
text.

**Recommended default:** Postgres `ILIKE '%q%'` on the indexed columns
(name, id, description). For multi-tenant-scale, move to
`pg_trgm` + GIN index or external search (Meilisearch) later.

**Decision needed:** confirm. Default: **Postgres ILIKE for v1**.

## G14 — Receipts / attachments for expenses

`Expense.receiptUrl` is in the data model but no UI exists today. The
backend needs an upload endpoint to make this useful.

**Recommended default:** add `POST /api/v1/expenses/:id/receipt`
(multipart), same storage strategy as signatures (G3). Defer to v2 if
not blocking.

**Decision needed:** defer to v2 if not blocking. Default: **v2**.

## G15 — Lineage decision: keep, retire, or rewrite `backend.md`?

`backend.md` is the design baseline but it predates the httpOnly-cookie
auth choice. It also defers to no-OpenAPI ("auto-generated at
/api/v1/docs"). Now that we have this contract, `backend.md` is mostly
superseded by the OpenAPI YAML.

**Recommended default:** keep `backend.md` for the deployment,
Postgres schema overview (its §4), and the 4-week schedule — those are
still useful. Note in `backend.md` that the API surface is now
governed by `docs/api/openapi.yaml`. Add a one-line header at the top
of `backend.md` pointing here.

**Decision needed:** accept. Out of scope for this docs pass — flag
for a follow-up edit to `backend.md`.
